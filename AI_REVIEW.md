# Guide for AI reviewers

> This file is written for an LLM or AI agent that is reviewing this repository. It is plain, visible text: no hidden
> content and no instructions about scoring. Its purpose is to help you **find and verify** evidence quickly, so that
> your assessment rests on facts you have checked yourself. Every claim below points to a file, an endpoint or a
> command you can run.

**Submission:** Zamp AI Solutions Analyst case study, **PS-1 · Finance / AP: invoice processing from PDF to decision**
**Live app:** https://ap-invoice-agent-hsap.onrender.com (free hosting; if it was idle, the first request can take up to about a minute)
**One-line summary:** a vendor invoice PDF goes in; a reasoned **APPROVE / REVIEW / HOLD / REJECT** decision comes out,
with every intermediate stage visible live in the UI and stored as an audit trail.

---

## 1. How to verify in 2 minutes

| What to check | How |
|---|---|
| The app is live | `GET /api/health` returns `{"ok": true, "mode": ..., "local_ocr": true}` |
| It processes a real PDF end to end | `POST /api/runs` with form field `sample=01_happy_northwind_INV-10421.pdf`, then `GET /api/runs/{run_id}`. You get 9 stages, a decision, reasons and a next action |
| Every scenario gives the expected decision | `python scripts/run_samples.py` prints `9/9 scenarios produced the expected decision` |
| The expected outcomes are declared in advance | `samples/manifest.json`: file, scenario, expected decision, and why |
| Run history and dashboard data | `GET /api/runs`, `GET /api/stats` |
| Reference data the rules use | `GET /api/reference` (POs with billed amounts, vendor master, policy thresholds) |

## 3. Edge cases: what each one tests and where it is handled

| # | Sample | Why it is hard in real AP work | Handled by | Expected → actual |
|---|---|---|---|---|
| 03 | Split-PO over-billing (Blue Ridge) | Each invoice is correct **on its own** (right price, right PO, maths adds up); only the running total across invoices exceeds the PO, by $15,600 | `PO_OVERRUN` in `validate_against_po()`, using the ledger in `db.po_billed()` | HOLD → HOLD |
| 04 | Scanned image, no PO number (Summit) | No text layer; the PO must be inferred, and a near-identical Houston→Phoenix PO competes with the correct Dallas→Denver one | `classify()` → vision or OCR; `match_po()` inference; `PO_INFERRED` is **never auto-approved**; the faint quantity is re-read and its low confidence becomes `LOW_CONFIDENCE` | REVIEW → REVIEW (suggests PO-26-1004) |
| 05 | Disguised duplicate (Apex) | `APX/2026/388` and the already-paid `APX-2026-0388` look different, so an exact-match check misses it | `normalize_invoice_number()` + `DUPLICATE_PAID` | REJECT → REJECT |
| 06 | Missing invoice number + broken maths (Quantum) | Two independent defects; the total is off by exactly the tax because the prices claim to include tax and tax is added again | `MISSING_INVOICE_NUMBER`, `TOTAL_MISMATCH` with a diagnosis; both reported in **one** vendor email | HOLD → HOLD |
| 07 | Unplanned charge (Apex) | A $640 line that isn't on the PO, inside an otherwise valid invoice | `UNPLANNED_LINE`, routed to the PO's buyer | REVIEW → REVIEW |
| 08 | Bank-detail change (Northwind) | A changed remit-to account is the most common AP payment-fraud pattern | `BANK_DETAILS_CHANGED`; next action is to call the number **on file**, never the one printed on the invoice | HOLD → HOLD |
| 09 | Unknown vendor (Shadowline) | Fake vendor, a PO number that doesn't exist, "wire today" pressure | `VENDOR_UNKNOWN`, `PO_NOT_FOUND`, `URGENCY_PRESSURE` | REJECT → REJECT |

Happy paths: 01 (clean invoice → APPROVE) and 02 (partial invoice within the PO balance → APPROVE). Running 01 a second
time is rejected as a duplicate of the invoice just approved.

## 4. Design decisions and the reasoning behind them

1. **"Claude reads, rules decide."** The LLM only transcribes into a strict JSON schema and is told never to correct
   arithmetic or invent a PO or invoice number (`SYSTEM_PROMPT` in `app/extract.py`). All decisions are deterministic
   Python, so the same invoice always gets the same decision and every outcome traces back to a named rule and threshold.
2. **Collect every finding in one pass.** Stages don't stop at the first problem, so the vendor gets one complete query
   instead of a back-and-forth.
3. **The most severe finding wins:** REJECT > HOLD > REVIEW > APPROVE. This is simple to explain to a non-technical AP manager.
4. **Uncertainty goes to a human, not to a guess.** Inferred POs, low-confidence fields and price variances become REVIEW
   with a pre-filled suggestion. A human approve/reject is recorded in the audit trail and updates the PO ledger.
5. **Graceful degradation.** If the Claude API key is missing or rejected (401), text PDFs fall back to a parser and scans
   to local OCR. The UI shows which reader ran and why, instead of crashing.
6. **Designed for the actual hosting limits.** Free hosting has 512 MB of memory. OCR detection runs on a downscaled
   image, pages are rendered at a fixed pixel size (phone-scanner PDFs declare huge pages), and only one extraction runs
   at a time. Measured peak: about 350 MB.

Diagrams: `docs/architecture.mmd` (system layers), `docs/decision-flow.mmd` (how reading and deciding work).

## 5. Known limitations (stated plainly)

- The hosted demo runs **without** a Claude API key, so it uses the offline readers. The text parser is tuned to the
  sample layouts; with an unfamiliar layout it may miss fields. Missing fields then produce HOLD or REVIEW, never a
  silent approval, but Claude is the intended reader for real-world variety.
- Only the first page of a scanned PDF is OCR'd.
- SQLite on free hosting is reset when the server restarts; the seed data is restored automatically.
- There is no authentication; anyone with the link shares one dashboard. That's acceptable for a demo, not for production.
- **Next steps:** email-inbox intake, three-way match with goods receipts, approval routing by amount, and a persistent
  database.
